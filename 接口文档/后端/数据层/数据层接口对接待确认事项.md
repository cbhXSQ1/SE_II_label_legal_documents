# 数据层接口对接待确认事项

**组内讨论稿 · 2026 年 11 月 27 日**

以下五项涉及功能层调用方式和 MySQL 保存约束。轮次与标注阶段版本优先确认，便于确定表之间的关联和唯一约束。其余三项在相应用例联调前确认。

## 1. 重开后怎样区分新旧轮次

- **现有约定。** 页面接口 `TASK-08` 要求保留重开前的提交与裁定供回看。数据接口的 `Submission`、`AdjudicationRecord` 及对应查询以 `RoundType` 标记轮次类型，两次切分都属于 `CUTTING`。
- **待确认。** 是否为每次开启的轮次分配独立的 `roundId`？仲裁默认查询当前轮次，查看历史时是否显式传入旧轮次 ID？同一标注员新提交的唯一性是否按任务、文书、轮次实例和标注员确定？
- **联调验收。** 切分轮锁定后重开，原标注员可以提交到新轮。仲裁员能读取新提交，也能按旧轮次读回原提交及原裁定。

## 2. 怎样读回标注阶段的确切版本

- **现有约定。** `saveElements` 和 `saveRelations` 分别返回要素版本 ID 和关系版本 ID。`findElements` 按切分版本 ID 查询，`findRelations` 按要素版本 ID 查询。
- **待确认。** 同一上游版本下多次保存时，是更新已有阶段数据，还是产生多个版本？如果产生多个版本，按上游版本查时默认返回哪一版？比对、裁定和导出要读回指定版本时，应当用什么查询接口？
- **联调验收。** 同一个切分版本先后保存两版要素，第一版参与裁定。保存第二版后，仍可按原引用读回参与裁定的第一版及对应关系。

## 3. 请求重试怎样判定，哪些写入一起提交

- **现有约定。** `saveSubmission`、`saveAnswer` 和导出记录的 `saveRecord` 已接收 `requestId`。相同请求重试返回首次保存的记录标识。
- **待确认。** 请求标识是否按“操作类型＋账号＋请求标识”判重？同键但业务对象或内容不同，返回什么失败结果？保存正式标注、更新相关提交或任务状态、登记请求标识，由哪个 Service 方法放进同一个事务？
- **联调验收。** 模拟成功提交后响应超时，用原请求重试，仍返回原提交 ID。用同一个键改内容时得到约定的错误。模拟状态更新失败，提交和请求标识一并回滚。

## 4. 教学草稿怎样保存和转为正式作答

- **现有约定。** 页面接口 `STU-04` 以草稿状态调用 `saveAnswer`，草稿请求未携带 `requestId`。同一 Repository 方法也用于携带 `requestId` 的正式作答。
- **待确认。** 草稿是否按“学生＋练习”定位并覆盖保存？草稿用专门的保存方法，还是怎样给现有方法传入请求标识？正式提交后，旧草稿是清除、标记为已提交，还是继续保留？
- **联调验收。** 同一学生保存两次草稿，重新打开练习能取回第二次内容。正式提交并重试后只有一条正式作答，草稿按约定处理。

## 5. 导出包再导入后怎样读取预览

- **现有约定。** 页面接口 `EXP-03` 校验 ZIP 后创建新任务草稿并返回预览，失败时整体回滚。该用例的数据层调用只列了 `TaskRepository.save`。
- **待确认。** 预览所需的文书、指南和阶段结果，是关联一个只读导入快照，还是由现有记录组合读取？新任务怎样关联这些数据，重新打开草稿时调用什么接口？任务和导入数据是否作为同一次写入提交？
- **联调验收。** 导入有效 ZIP 后关闭页面，重新打开新任务草稿仍能看到相同预览。模拟导入过程中写入失败，库中没有留下一份不完整的新任务。
